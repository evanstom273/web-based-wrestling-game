# Agent / contributor instructions

This repository is a serious code-driven 3D professional-wrestling game. Treat the architecture as a product constraint, not a suggestion.

## Stack is fixed

Use the existing stack from the beginning: Vite, React, TypeScript, Tailwind CSS, Three.js/WebGL, React Three Fiber, Drei, Rapier, Zustand, Vitest, Playwright, ESLint, Prettier and GitHub Actions.

Do not replace core stack choices casually. Do not remove Rapier or tests because a feature appears simple.

## Hard architecture boundaries

1. **React + Tailwind own application UI.** Menus, HUD, settings, wrestler selection, results and responsive controls belong here.
2. **Plain TypeScript owns authoritative wrestling simulation.** Match state, move legality, damage, stamina, momentum, AI, pins, submissions, reversals and rules must be testable without React or WebGL.
3. **R3F + Three.js own presentation.** Scene graph, procedural geometry, lighting, camera, particles and visual animation consume simulation state; they do not invent match results.
4. **Rapier owns spatial physics/collision.** Use it for bodies, boundaries, ring/world collision, weapons and environmental physics. Wrestling move outcomes remain controlled by the match engine rather than accidental ragdoll physics.
5. **Zustand is a bridge, not the match engine.** It may expose UI/render snapshots and app state. Do not bury domain rules in Zustand actions.

## Rendering philosophy

The default visual pipeline is programmatic/code-driven 3D art. Prefer primitives, generated meshes, materials, shaders, instancing and procedural composition. A wrestler, ring, arena prop or crowd member should be capable of being described as data and generated by code.

External models/textures are allowed only when they clearly improve the game and are deliberately adopted. Never make imported assets a hidden dependency for core gameplay.

## Wrestling-system rules

- Build moves as data plus reusable execution/animation logic, not one-off component hacks.
- Model wrestling positions explicitly. Do not reduce wrestling to generic hitboxes and HP.
- Keep simulation timestep independent from render framerate.
- Keep AI on the same legality/rules layer as the player.
- Procedural animation may drive moves, but move resolution belongs to the simulation layer.
- Physics should enhance impact and environment interaction without making match logic nondeterministic by accident.

## Quality bar

TypeScript stays strict. No `any` unless justified at an unavoidable external boundary. Avoid giant god components/classes. Prefer small modules with explicit ownership.

Every gameplay rule should be unit-testable. Every user-critical browser flow should eventually have a Playwright test.

Before a PR is considered ready, run:

```bash
npm run format:check
npm run lint
npm run typecheck
npm run test
npm run build
npm run test:e2e
```

## Responsive requirement

Desktop is not the only target. Every UI feature must remain viable on phone, tablet and foldable layouts. Touch targets must be practical, and 3D input must have a touch equivalent where the feature requires direct control.

## Git workflow

Work on feature branches and merge through pull requests. Keep commits focused. Do not use repeated direct commits to `main` for iterative development.
